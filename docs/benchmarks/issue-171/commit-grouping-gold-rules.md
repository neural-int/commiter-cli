# Commit Grouping Gold 作成・採点規則

**Version:** 1.0  
**用途:** [#171](https://github.com/neural-int/commiter-cli/issues/171) のDirect Grouping比較検証に用いるGold作成・採点契約  
**位置付け:** 研究用規範。Production仕様の変更ではない。

## 1. 基本原則

Goldは、与えられたGit変更ファイル集合を**変更目的**に基づいてコミット単位へ分割した正解データとする。

1. 同一変更目的のファイルは、原則として同一コミットに統合する。
2. 独立した変更目的のファイルは、原則として別コミットに分離する。
3. **1ファイルを複数コミットに分割しない。** hunk単位の分割は対象外とする。
4. 各変更ファイルは、必ず1つのコミットにのみ所属する。
5. ファイル不可分性と変更目的の同一性を優先し、その範囲内でRevert独立性を考慮する。

## 2. 変更目的の判定

### R1. 同一変更目的

**同一の具体的な振る舞い・機能変更・バグ修正・契約変更**を実現する変更を同一変更目的として扱う。具体的には、同じ変更の実装、直接必要な対応テスト、利用側の変更、設定変更などを含む。

ファイル・関数・パッケージ・変更種別の違いだけを理由に分離しない。

### R2. 独立した変更目的

実現する振る舞い・機能目標・修正対象・契約が異なり、一方を取り消しても他方の変更目的が意味的に成立する場合は、異なる変更目的として扱う。

同一ファイル・関数・パッケージ・ヘルパーの共有や、単なるコード参照関係だけを理由に統合しない。

### R3. 実質的依存

次のいずれかが具体的に確認できる場合、実質的依存があると判定する。

- 一方のインターフェース・契約変更に、他方の対応変更が必要である。
- 一方を取り消すと、他方の変更後の振る舞いや契約が成立しなくなる。
- 両者が同一の振る舞い・契約変更を成立させるために不可分である。

**実質的依存は同一目的の十分条件ではない。** 依存があっても独立した機能目標が確認できるなら異なる目的として扱い、依存関係だけで統合しない。

## 3. ファイル単位のグルーピング

### R4. 1ファイル1変更目的

1ファイルが単一目的に属する場合、同じ目的を持つ他のファイルと統合する。ただしR7の優先規則を適用する。

### R5. 1ファイル内の複数目的候補を統合できる場合

1ファイルに複数の変更目的候補が存在しても、**それらすべてが実質的に依存し、1つの具体的な振る舞い・契約変更として成立する場合のみ**、単一目的として扱う。その目的に属する他のファイルも統合する。

### R6. 1ファイル内に独立した目的が残る場合

1ファイルに複数の変更目的があり、R5の条件を満たさない場合は、**そのファイル単独で1コミット**を構成する。

- 特定の目的のグループへ恣意的に割り当てない。
- 関連する他ファイルを、その単独コミットへ追加しない。
- 同じファイルを複数コミットに重複させない。

目的が2つでも3つ以上でも同じ規則を適用する。例えばAとBが依存しCが独立する場合も単独コミットとする。依存グラフが連結していることだけではR5を満たさない。

### R7. 複数目的ファイルの優先規則

R6による**単独コミット規則はR1・R4の同一目的統合より優先**する。

このため、同一目的の関連変更が別コミットへ分散しても、R6に従えばGold上の正当なFallbackとする。ただしFallbackによる目的分断は、通常の意味的Grouping成功とは別に記録する。

## 4. Revert可能性

### R8. 独立目的のRevert分離

独立した変更目的は、可能な限り別の目的を巻き込まずにRevertできるコミットへ分離する。ただしRevert可能性を理由にR1〜R7の結果を変更しない。

### R9. 複数目的ファイルの例外

R6による単独コミットは複数の独立目的を含むことを許容する。そのため目的ごとの独立したRevertができなくてもGoldの誤りとはしない。

### R10. Revert保証の範囲

Goldは独立目的の不要な混在を避けるためのものとし、任意のRevert順序でビルド・テスト・実行時動作が維持されることは保証しない。

## 5. Gold作成手順

1. 各変更箇所の具体的な変更目的を識別する。
2. R1〜R3で同一目的・独立目的・実質的依存を判定する。
3. ファイル内の目的数とR5の統合可能性を評価する。
4. R4〜R7を適用し、各ファイルのコミット所属を決定する。
5. 全変更ファイルの割当漏れ・重複、不要な独立目的の混在を検査する。
6. R8〜R10の範囲内でRevert独立性を記録する。

## 6. 証拠・不確実性

### 6.1 判定証拠

Git差分、関連する既存コード、明示された仕様から確認できる事実に基づく。同一ファイル・パッケージ・作業・共通ヘルパーというだけでは目的の一致を認定しない。依存や作者意図が観測できない場合は推測で確定しない。

### 6.2 Goldの確定状態

| 状態 | 定義 | 評価 |
|---|---|---|
| `confirmed` | 根拠に基づき一意のGoldを決定できる | 主評価に含める |
| `multiple_valid` | 複数の分割に合理的な根拠がある | 許容解集合を**推論前に**固定し、主評価と区別して報告 |
| `undetermined` | 正解自体を確定できない | 主評価から除外し、理由・件数・除外率を報告 |

**Goldの確定可能性とモデル入力からの識別可能性は異なる。** Goldがconfirmedでも、Baseline・Treatmentの各入力に必要情報がないことがある。両armでGoldは共通とし、入力情報充足性をarm別に記録する。Goldが確定しているケースを「モデル入力で識別不能」という理由のみで事後除外しない。

### 6.3 保存する情報

各fixtureについて、変更ファイルID集合、各ファイルの目的ID、目的間の関係、具体的なsource根拠、適用規則、Gold partition、Fallbackファイル、fallbackによる目的分断、確定状態、arm別入力識別可能性を記録する。

モデルへGold・作者の元commitメッセージ・評価rubric・fixture種別を送らない。Gold、許容解、採点関数、除外判断を最初のモデル生成前に固定し、事後に変更しない。

## 7. 採点規則

### 7.1 正規化された分割

ファイルIDを要素とするグループの**集合の集合**として比較し、グループID・コミット並び順・グループ内順序は無視する。すべての選択ファイルは過不足なくちょうど1グループへ所属する。

### 7.2 Exact Partition

予測分割とGold分割が正規化後に一致すれば1、それ以外は0。主指標は`confirmed` fixtureに対するfixture単位の完全一致率とする。構造不正や応答失敗も0として別途失敗理由を記録する。

### 7.3 False Merge（FM）

Goldで**別グループ**の2ファイルが予測で**同じグループ**に入った場合をFM 1ペアとする。

### 7.4 False Split（FS）

Goldで**同じグループ**の2ファイルが予測で**別グループ**に入った場合をFS 1ペアとする。

FM/FSは**ペア件数**と**FM/FSを1件以上生じたfixtureの件数・率**を区別する。R6/R7で許容された単独コミットから生じる意味的な目的分断は、Goldへの不一致に由来するFSとしては数えず、Fallback由来の目的分断として別計測する。

### 7.5 Fallbackと構造条件

R6による単独コミットがGoldと一致するならExact上は正解。ただしFallback件数、関連目的を分断した件数、全件singletonへの偏りを別記録する。全件mergeについても同様に偏りを検知する。

全ファイルのexactly-once所属、未定義IDなし、JSON Schema適合を必須とする。構造的に不正な予測はExact不正解とし、FM/FSが算出不能な場合は0件と偽らず`unscorable`として別計上する。

## 8. 適用範囲

本規則はファイル単位のGoldとGrouping評価に適用する。hunk単位の分割、部分的staging、任意順のRevert安全保証は対象外。モデル入力とGold作成者が参照した情報に差がある場合は、意味判断失敗と情報不足を別々に分析する。

この文書は**Gold作成・採点規則**のみを定める。#171のfixture一覧、実際のGoldデータ、完全なprompt/schema、モデルpin、Gate数値、call/resource上限は、Phase 0で別途生成前に凍結する。

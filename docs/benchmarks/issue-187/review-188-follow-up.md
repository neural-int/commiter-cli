# PR #188: renameとRPC無応答の追加レビュー対応

確認日: 2026-11-03。基点は`8483a874`。保存fixture・過去のモデル生成結果は変更していない。

## RPCの無応答

履歴取得全体の固定期限を戻さず、各RPCで30秒進捗がなければ入出力pipeを閉じる。応答データの到着で無通信時間を更新するため、大きな応答や複数ページの収集は全体で30秒を超えても継続できる。別IDの応答や通知だけでは当該RPCの進捗としない。

親キャンセルと応答サイズ・メモリ保護を維持する。停止理由はrpc_idle_timeout、モデル向け理由はhistory_unavailableとする。通常Collectでは取得済み任意履歴も除いてGitの固定差分だけで続行する。snapshot検査と生成の検証は省略しない。

模擬App Serverで完全無応答、JSON途中で停止、並列workerの途中停止、通知だけの送信を検査する。期限を超えて小分けの応答が届く場合は取得を継続できる。実App Serverを意図的に停止させた実機試験ではない。

race検査の初回は進捗継続ケースが最初の応答前にテスト用200ms期限へ達した（受信0 bytes）。そのケースだけ期限を1秒、分割応答を約1.6秒へ変更し、全体の親guardを15秒とした。製品の30秒設定は変更していない。

## 純粋rename

通常のテキストファイルで、hunkを持たず100%一致のrenameメタデータだけがある場合、送信するraw_diffのメタデータ範囲を指す仮想ブロックを作る。これにより通常の投影から既存comparisonBlocksへ到達できる。バイナリ・opaque等の内容を公開する例外は設けない。

旧新パスと完了したrename操作を照合する。候補があっても内容の編集成功を断定せず、ambiguous・rename_content_unverifiedとして保持し、候補のmatchはpartialとする。複数操作、別の移動先、本文欠落、同パスの通常編集も回帰対象とする。

## 組み合わせ探索の測定

モデルと実履歴を使わず、単一の現在追加ブロックと、2つの過去パスに分布する無関係な追加ブロックを用意し、markSplitMergeEvidenceだけを各規模1回測定した。履歴側の2パスも選択ファイルに含め、その現在の混合追加・削除ブロックは断片探索の対象外とした。

Apple M3・Go benchmark、benchtime=1x・count=1。OS負荷・温度を統制していない合成の診断値で、割当は累積でありピークRSSではない。無関係な履歴でも負荷が増えることを観測したが、実履歴での通常CLIの遅延・メモリ増分は未測定。今回はmappingのアルゴリズムを変更せず、最適化の追加検証対象として残す。

最初の診断では履歴側の2パスを選択ファイルに明記しておらず、5,000件で356.460ms・807,085,128 bytes/opだった。選択パス制約を明示するため入力を補正して再測定した上表と区別し、速度改善の比較には使わない。

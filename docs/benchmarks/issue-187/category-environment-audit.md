# Issue #187: 7・9ファイルのCategory採点と実行環境の監査

確認日: 2026-11-03。

## 結論

7・9ファイルのCategoryを誤分類とした原因は、元goldのfeatラベルを使った採点だった。対象は不具合修正であり、保存済みモデル出力のfixは妥当だった。正解をレビュー差分として訂正すると、両経路とも7は4/4、9は5/5、11は5/6になる。11の同じ変更に対するfeat出力は誤分類として残る。

保存入力の欠落、参照の取り違え、予算超過、Categoryへの前フェーズKVの流用は確認されなかった。実行環境については、以下の限定した対照4条件すべてで元の全Category出力と一致した。既知fixture各1回の結果から、環境の影響を一般に否定したり、全体の意味品質を保証したりはしない。

## 監査範囲と事前登録

保存済み7・9・11ファイルの要求・応答・fixtureを読み取り、7・9ファイルで誤分類と記録した変更を調べる。元fixture、元gold、生成応答、過去の測定値は変更しない。通常Planner、プロンプト、モデル、sampling、制約、予算も変更しない。

静的監査では、sourceから004への再投影が保存要求と完全一致し、Categoryに全ファイルの差分・変更ブロック・final-only履歴が残り、候補のcontext_refが解決することを確認した。各ケースのoracle/propagated Category要求と生成JSONも完全一致した。

正解ラベルに問題が見つかった。対象は全ケースで同一のF3/F5（G003）で、保存goldはfeatだが、変更内容は空のMessage-IDの正規化とメールキー衝突の修正である。凍結before/afterの正規化関数を抽出して実行すると、beforeは`<>`と空白付き`<>`をそのまま返し、afterはNoneを返す。`< >`は両方でNone、有効なIDの正規化は同じだった。既存関数のdocstring、追加した回帰テスト、モデルへ実際に渡した最終応答も不具合修正を支持する。過去の004比較報告にも、この変更の期待値をfixへ訂正した記録がある。今回のrun004はその確認済みコピーではなく、元のfeatラベルを含むgoldを読み込んでいた。

追加の原因切り分けは最大4生成とする。元測定helperと検証済み最終helperそれぞれで、7・9の保存済みoracle Category要求を新規プロセスの`--benchmark-single`に1回ずつ渡す。要求本文はbyte単位で維持し、モデル資産追加、warmup、再試行、prompt/seed調整を行わない。元ランナーと同じ開始条件を各呼び出し前に適用し、別ファイルに監視・応答・失敗を保存する。既存warmセッションとの比較は、先行Grouping/Textおよび保持状態をまとめて除いた対照であり、各要因を独立に変えた因果実験とは呼ばない。

新たな生成は正解を修正するためには不要で、実行環境・セッション状態の確認にのみ用いる。結果を見て追加呼び出しを増やさない。

訂正は出力を期待値へ合わせるためではない。before/afterの挙動、回帰テスト、既存の欠損IDフォールバック仕様、実入力の変更説明、過去のレビューがfixを支持する。とはいえ同じエージェントによるレビューであり、独立した人手評価ではない。この表はCategoryのtypeだけを採点し、breakingやTextの意味品質の全面的な認証には使わない。

[レビュー差分](category-gold-review.json)に元goldのSHA-256、対象ファイル集合、変更前後の期待値、両採点を記録した。[入力監査の集計](category-input-checks.json)には3ケースの要求再構築・証拠保持・参照解決・採点の検査結果を記録した。元goldのファイルhashは不変だった。

## 入力とruntimeの切り分け

- sourceから再構築した全3フェーズの要求は保存要求と完全一致した。Categoryの全ファイル・raw_diff・change_blocksと最終応答辞書をsourceと比較し、表示契約上の省略以外に欠落・切断がなかった。対象のG003と参照する履歴は7/9/11で同一だった。
- F3/F5の候補は存在するH2を参照しており、別のUI変更への誤配属はなかった。元のhistory_incomplete/ambiguousを保持し、完全取得や一意な照合へ改変していなかった。
- CategoryのSchemaはfeatとfixの両方を許可していた。Category要求に固定typeはなく、正解ラベルはモデルのCategory入力へ注入されていない。helperの004処理もメッセージをそのままchat templateへ渡していた。
- 保存済みCategory入力は7が4,906 tokens、9が6,351 tokensで、64Kから4,096出力予約を引いた上限以内だった。予算超過による省略・再準備はなく、各1回の準備、completed、エラーなしだった。
- Categoryは独立prefillで、両ケース・両経路ともKV再利用0だった。各要求で新しいgrammar matcherを作り、sampling用RNGもseed 144で生成する。保持するモデルやgrammar用tokenizerと、前の出力を進めたmatcher/KVを区別して確認した。
- 元ランナーはCOMMITER_から始まる環境変数を除いた環境でhelperを起動していた。要求上のpinned Qwen・64K/4096と、004のThinking OFF、temperature .6/top_p .95/top_k 20/seed 144は想定条件に一致した。

最初の追加実行は、サンドボックスがsysctl/ioreg等の読み取りを拒否して監視段階で停止した。生成は0回で、失敗記録を保持した。読み取り用の実行権限で同じ最大4呼び出しの監査を再開し、監視を無効化しなかった。モデル失敗や再生成として扱わない。

元測定にはOS全体のswap/compressionと他プロセスの負荷があり、速度・資源の比較には交絡が残る。Category区間の温度は7がnominal/fair、9がnominal/fair、低電力モードは両方OFFだった。この観測だけから、環境が誤分類を起こしたとも、すべての数値的影響がないとも主張できない。

事前登録した4条件がすべて正常終了し、監視エラーはなかった。モデルとgrammarを要求ごとに新規プロセスで読み込み、先行フェーズと保持したprefix snapshotを除いた。両helperとも、7・9の全カテゴリが元の固定・伝播Category結果と一致した。対象G003は全4条件でfixだった。

確認した範囲では、先行フェーズの保持状態や2つのhelper版の違いによって7・9のCategory出力は変化しなかった。従って、今回誤りと数えた2件をその状態や環境の問題として説明する証拠はなく、確認できた原因は採点goldの選択・レビュー引継ぎの誤りである。

## Text評価への影響

元の固定Text要求は全ケースでG003のtypeをfeatに固定していた。従って、そのText結果はレビュー後の分類を正解とした対照ではない。一方、7/9の伝播Textには実Category出力のfixが渡っていた。保存済み要求でこの差を確認した。訂正した固定Textの再生成は今回行っていない。

## 検証範囲

この監査は既知のfixtureと保存応答の再解析で、新規holdoutによる品質評価ではない。プロンプト、製品コード、正解の原本、過去の測定応答を変更せず、今回の変更は監査と派生報告に限定する。Pythonの既存表示・投影テスト24件は成功した。remote CI、commit、pushは今回実行していない。

# H182-011 誤りの傾向と入力投影の分析

## 結論

観測上の主な難所は、(1)ファイルを変更目的でまとめるGrouping、(2)正しい判断を指定言語・scope・短文へ変換するTextである。一方、モデルへの入力前にコマンド14件と目的Bの会話本文が省略されたことを追加確認した。モデルの能力不足だけで説明しない。

結果報告: https://github.com/neural-int/commiter-cli/issues/182#issuecomment-6412409939
入力投影の補足: https://github.com/neural-int/commiter-cli/issues/182#issuecomment-6412593558

分析に追加のモデル推論は使っていない。原本の18セル・実行契約を変更せず、非推論で投影だけを再現した。以下の数は一つのfixtureに対する18条件の記述集計で、独立した18標本から一般的な失敗確率を推定したものではない。

## 1. Grouping：目的とファイルの関係を保てない

| 観測 | セル数 | 具体的な失敗 |
| --- | ---: | --- |
| 過剰統合のみ | 5 | A/B/Cの独立目的を全て一群にする |
| 過剰分割のみ | 4 | 全5ファイルを一つずつに分け、実装と対応テストを離す |
| 統合と分割の両方 | 7 | 無関係なファイルをまとめる一方、対応テストを分離する |
| 正解partition | 2 | Qwen3.5-4B Thinking ONの制約あり／なし |

統合誤りを含む条件は12/18、分割誤りを含む条件は11/18。両者は重複する。重い側の誤りが統合だけとは言えず、目的単位の判断の不安定さとして捉える。

例：Qwen2.5-3Bは両制約条件で全5ファイルを分割し、Coder-3Bは両条件で全て統合した。Coderであることが今回の目的別Groupingの優位性を保証していない。4B OFFにも誤りがあり、4B ONだけが3群を復元したが、各条件1回なのでThinkingの一般的効果とは断定しない。

## 2. Text：内容理解と出力契約は別問題

4B Thinking ONの両条件は、Grouping3/3、Category3/3、breaking=noneだった。最終Textは次のscopeを返した。

- README群: docs
- UI群: feat
- メール正規化群: fix

いずれも現行validatorがscopeとして許可しないConventional Commit type名であり、対象コンポーネントとtypeの役割を混同している。全summaryも英語だった。送信payloadにはsummary_language=jaが存在し、systemにもscopeはtype名ではないと明記されている。日本語条件が全く渡っていなかったわけではない。

両制約条件の最終回答は同一内容で、Thinkingの強制終了もない。構文マスクの有無やThinking打ち切りだけでは今回のText失敗を説明できない。グループや変更目的は把握できても、最後に複数の出力条件を同時に守るところで失敗している。

改善候補は、意味の通るコンポーネントscopeと日本語短文を含むフェーズ固有の例、systemでの日本語出力の直接明示、typeとscopeの区別の簡潔化。効果は未検証であり、この分析では実装・再測定していない。

## 3. 小型モデル：グループに応じた文章の選択と圧縮

- Qwen2.5-1.5Bの制約ありでは、差分にない.dev.pyの修正を記述した。READMEにある参照先の説明と、そのファイル自体の変更を取り違えている。
- Coder-0.5Bの制約ありは全5グループに同じ品質チェック説明を反復した。各群の変更内容に応じた説明の切り替えができていない。
- 全変更を統合したセルではREADME中心の説明が多く、メール修正・UI機能を落としている。Groupingの失敗がTextの対象選択にも波及する。
- Coder-0.5B、Coder-3B、Qwen3.5-2Bの制約ありで、48文字上限に達し、読点、接続助詞、typecheckの語の途中で終了する応答を観測した。これは生成後のホストによる切り詰めではない。上限以内で意味を完結させる短文化ができていない。

READMEが先頭にあり参照先や手順の本文もあるため、説明しやすいREADMEへ注意が偏った可能性はある。ただしファイル順や本文量を変えた比較はなく、位置バイアスの因果効果は未確認。

## 4. Category：docsとfeatの区別、breakingの不確実性

READMEを単独群にできた7セルのうち、docsと判定したのは3セル。残る4セルはfeatとした。文書の追加とアプリの機能追加を区別できない例がある。

Coder-1.5Bは両制約条件で全3群へunresolvedを返し、Categoryで停止した。JSON形状の失敗ではなく、破壊的変更の不確実性を解消できなかった停止である。noneへ強制変換して成功に数えない。現行ルール上、疑いを保守的に残すこと自体は許容されるため、出力だけで全てを不適切な誤報と断定しない。

Categoryは先行するGroupingに依存する。今回は正解群だけを分母にする評価であり、非Thinking条件で正解A/B群を与えた独立Category評価はしていない。Categoryのモデル能力だけを切り出して順位付けできない。

## 5. 入力側の問題：取得と送信の間で重要な情報が落ちている

取得・凍結した履歴には14コマンドと3コンテキストの依頼・最終応答がある。しかし全18 Grouping要求でコマンドは0件、H3の依頼と最終応答も空になっていた。目的Bの実装は4ブロックとも内容照合候補がなく、目的Bのテストが参照するH3の会話本文も省略されている。目的Aのテストも候補がない。

非推論再現の結果はprojection-replay.json。実送信payloadの完全再現を確認した。

| 枠 | コマンド | H3の会話本文 | 結果 |
| --- | ---: | --- | --- |
| 16k | 14→0 | 依頼・最終応答とも省略 | 元の送信payloadと完全一致 |
| 32k | 14→14 | 両方保持 | 省略なし |
| 64k | 14→14 | 両方保持 | 省略なし |

必須入力から16kを選んだ後、補助履歴で枠を広げない実装が、UTF-8バイト長による見積もり22,364を16kに収めるため、省略を行った。実tokenizerのcontextが16kに到達したという証拠ではない。入力保持を改善できる余地はあるが、32kでモデルのGrouping精度が上がるかは未検証。

取得自体もpartial/history_incomplete、全9ブロックambiguousだった。これらと投影時の省略は別の問題であり、分けて計測・表示する必要がある。今回の結果を「コマンド補助を全件渡してもモデルが使えなかった」と解釈してはいけない。

## 6. 形式制約が解決した範囲

文法制約あり26/26 phaseがJSON解析・Schema適合。なしは24 phase中22 JSON解析、17 Schema適合。JSON Schemaは構造と長さを守るのに有効だったが、言語、scopeの役割、目的別Grouping、説明の事実性は別の評価である。validator受理6セルも全てGrouping不一致であり、意味的正解の代用にはならない。

## 7. 優先する切り分け案

1. 入力投影を先に点検する。取得件数に加え、実送信件数・本文省略・理由を記録し、履歴を保持した比較条件を用意する。文法・prompt変更と同時に効果を測らない。
2. 4B Thinking ONで正しかったGrouping/Categoryを固定する診断を別立てにし、Textの日本語・scope・短文化を検証する。診断成功を実Grouping込みE2E成功と混同しない。
3. Groupingは、完全な履歴投影を使う条件と、現在の入力または履歴なしの条件を同一fixtureで比較し、モデル差と入力差を分離する。
4. README-onlyのdocs分類とbreaking境界を、小さなCategory診断で確認する。

ここでは修正や追加モデル推論を行っていない。モデルが主観的に難しいと感じた内容は測定できないため、以上は実出力・処理経路に基づく難所の分析である。

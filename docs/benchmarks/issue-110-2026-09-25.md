# Issue #110: Ollama / MLX planning benchmark (2026-09-25)

## Status

**Provisional.** The same planning schema and synthetic repository input were sent to both production adapters. The current MLX configuration failed all five multi-commit trials after the single repair and exhausted the output budget for a 24-file input at 1152, 2048, and 4096 tokens. These failures prevent a production default decision or a defensible final numeric output contract. The existing Ollama default remains appropriate pending remediation and a repeated benchmark.

## Environment and method

- Apple M3, 16 GiB unified memory, macOS 26.6.2 (arm64).
- Repository baseline: `6e087f5cffbaa0c6594e6f01df968ef4fdcb12d3`.
- Ollama 0.33.3 on Metal, `qwen3.5:4b-q4_K_M`, digest `2a654d98e6fba55d452b7043684e9b57a947e393bbffa62485a7aac05ee4eefd` (GGUF Q4_K_M, 3,389,983,735 bytes).
- MLX release helper from this checkout, Apple Swift 6.4 and pinned `mlx-swift-lm` revision `c6446cf7bfb7cea76408013b614d4b2c530eaa03`. Model: [`mlx-community/Qwen3.5-4B-MLX-4bit`](https://huggingface.co/mlx-community/Qwen3.5-4B-MLX-4bit) at `32f3e8ecf65426fc3306969496342d504bfa13f3`, 4-bit, 3,061,129,077 bytes. The two model artifacts have different quantization formats, so observed differences include artifact effects.
- The local [benchmark harness](../../tools/benchmark110/main.go) uses `planning.Schema`, `planning.Renderer`, `contextinput.Prepare`, and `planning.Generator` for both adapters. It uses only synthetic diffs and structural evidence. It stores numeric observations, violation codes, types, and file IDs; it does not persist prompts or generated text. Each run is sequential. The generator's wall clock starts after input preparation, includes helper launch/model load and an optional repair, and ends after plan validation. It excludes repository collection and Git mutation.
- The normal, multi-commit, and Japanese fixtures were repeated five, five, and three times per backend. Large diff and 64K cases were run once per backend. Output budget was 1024 tokens unless noted. `reference_grouping` compares only clear fixture grouping expectations; a successful plan has already passed the production grammar and domain validators.

## Results

| Fixture | Input / context | Ollama | MLX | Planning-quality observation |
| --- | --- | --- | --- | --- |
| Normal, implementation + test | 3,690 bytes / 8K | 5/5 valid; median 8.54 s (7.71–11.69) | 5/5 valid; median 6.60 s (6.54–6.80) | Expected single group: Ollama 4/5, MLX 5/5. |
| Two independent changes / multi-commit | 4,598 bytes / 8K | 4/5 valid; median 18.99 s (15.33–110.14) | 0/5 valid; median 24.83 s (23.74–26.93) | Ollama's four valid plans matched the two reference groups. MLX returned `invalid_scope` on all ten initial/repair candidates. |
| Japanese summary | 3,719 bytes / 8K | 3/3 valid; median 10.24 s (9.53–11.07) | 3/3 valid; median 33.75 s (24.65–68.85) | All six passed Japanese-language validation and the reference grouping. |
| Large diff | 26,400 bytes / 32K | 1/1 valid; 41.46 s | 1/1 valid; 26.20 s | Ollama split implementation, test, and docs into three commits; MLX grouped them together. |
| Near 64K | 54,692 bytes / 64K | 1/1 valid; 164.48 s | 1/1 valid; 137.44 s | Both completely assigned six file IDs. This case measures context size, not semantic grouping quality. |

The multi-commit Ollama failure involved one initial `invalid_scope` and one repair candidate with `invalid_json`. MLX attempted the one permitted repair in all five multi-commit runs; no repaired candidate succeeded. A separate first pilot also failed for each backend on this fixture. No partial plan was accepted.

| Output stress | Production budget / result |
| --- | --- |
| 12 independent files, MLX | 1024 tokens: valid one-commit plan, 16.12 s. |
| 16 independent files, MLX | 1024 tokens: valid one-commit plan, 20.25 s. |
| 20 independent files, MLX | 1024 and 2048 tokens: `max_tokens`, 54.65 s and 116.94 s. |
| 24 independent files, Ollama | 1152 tokens (`48 × 24`): valid 12-commit plan, 806 decode tokens, 74.79 s. |
| 24 independent files, MLX | 1152, 2048, and 4096 tokens: `max_tokens`, 74.84 s, 137.73 s, and 208.25 s. At the helper maximum of 8192 tokens, a 9-minute deadline expired without a plan (540.26 s). |

All `max_tokens` and deadline attempts failed closed and produced no accepted plan. The 8192-token run was recorded as `backend_error` by the original harness, but its 540.26-second duration matches the configured 540-second context deadline; a separate 1 ms deadline probe verified the harness's explicit `deadline_exceeded` classification after that instrumentation was corrected. The precise helper stop state of the 8192-token run is unavailable. Successful large-file trials demonstrate that the 0.6B probe alone must not determine a low file cap; the 20–24 file MLX trials also show that the current `48 × files` reservation cannot yet be certified for the intended 4B model.

## Metric availability and limits

- **First request after process start:** the initial normal pilot was 11.24 s for Ollama and 9.42 s for MLX. The OS filesystem cache was not cleared, so these are not true cold-cache measurements.
- **Warm load / reuse:** Ollama's production request sets `keep_alive: 0`; MLX launches a new helper for every request. There is no retained-model reuse path to measure. On five subsequent normal Ollama runs, median reported model-load time was 2.14 s. MLX returns no load-duration field.
- **Throughput:** on the five normal Ollama runs, median prefill was 287.8 tokens/s and median decode was 21.2 tokens/s. The current MLX helper does not return prefill/decode counts or durations; those rates are unavailable and must not be inferred from total wall time.
- **Peak unified memory:** neither adapter exposes a comparable peak unified-memory metric. Process RSS omits or misattributes GPU allocations, so no peak value is reported.
- **Failure rates:** the denominators above are small synthetic samples, not production traffic. Model output varied even with identical input, and later MLX Japanese runs were much slower than the first pilot. Thermal state, OS cache, and memory pressure were not controlled. These numbers are diagnostic, not a stable performance ranking.
- **Privacy:** the pinned `mlx-swift-lm` source still logs a generated-text prefix in `GuidedGenerationLoop` even when `diagnosticLog` is false. Only synthetic inputs were used here. Production-content benchmarking and default adoption need a published, verified dependency fix or equivalent remediation.

## Bounded-output and specification decision

The schema currently bounds `commits` and each `file_ids` array by the required file count, but leaves `scope` and `summary` without numeric maximum lengths. `contextinput` reserves `max(1024, 48 × files)` output tokens; the MLX helper clips a requested maximum to 8192. The Japanese and English SRS currently state the 48-token-per-file reservation and an unlimited commit count. The observed `max_tokens` failures and multi-commit validation failures do not justify replacing those values with a claimed safe production limit yet.

Keep the current Ollama default. Resolve the repeated MLX `invalid_scope` repair failure, expose or otherwise measure MLX generation counts/timings and peak memory, decide the intended file/commit/string/output-token envelope from representative 4B trials, then update both SRS versions and #88 Acceptance Criteria together. Do not infer an MLX default switch from successful latency cases.

## Reproduction

```sh
GOCACHE=/tmp/commiter-issue110-gocache go run ./tools/benchmark110 -describe -fixture all
GOCACHE=/tmp/commiter-issue110-gocache go run ./tools/benchmark110 -backend ollama -fixture normal -repeats 5 -output-tokens 1024
GOCACHE=/tmp/commiter-issue110-gocache go run ./tools/benchmark110 -backend mlx -fixture normal -repeats 5 -helper mlx-helper/.build/release/commiter-mlx-helper -output-tokens 1024
GOCACHE=/tmp/commiter-issue110-gocache go run ./tools/benchmark110 -backend mlx -fixture many_files -many-file-count 24 -helper mlx-helper/.build/release/commiter-mlx-helper -output-tokens 0
```

The MLX model must first be explicitly acquired using the harness's `-prepare-mlx-model` option, which pins and verifies its revision. The Ollama daemon and listed model must already be installed. All inference stays local.

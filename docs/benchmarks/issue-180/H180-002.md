# Issue #180: 標準ハーネス H180-002

## 要約

2026-10-19、ユーザーの明示判断により改善②「語彙・空白token判定などの不変データを計画内で保持」を成果として採用した。次回以降は改善①cache一括評価も含む **H180-002** を標準ハーネス・比較baselineとする。旧標準H180-001の契約は[保存版](H180-001.md)に保持する。

次回の比較契約は `baseline_harness_id: H180-002` とする。実行する構成は `harness_id` に記録する。同じ構成の再測定では同じIDを維持し、変更候補には新しいIDを割り当てる。IDは構成、iterationは測定回を識別する。過去契約のbaseline_harness_idは当時の比較元なので書き換えない。

H180-001のmodel/tokenizer保持、Category/Text共通prefix KV再利用、不要logits評価除去、`eval(cache)`を維持する。不変のGrammarTokenizer、空白token ID、runtime stop ID、EOS/unknown metadataを一計画で一度構築し、Grouping/Category/Textの再利用を `[false, true, true]` とする。schema別constraint/matcher/native stateはphaseごとに新規生成し、計画間では共有しない。

thinking予算512/384/384、seed144、temperature0、topP1、topK0、chunk512、model/revision、prompt、schema、出力/context条件は前標準を継承する。同期とMemory.clearCache()の頻度は変更しない。改善③は未実施。

## 考察

全体時間の一律短縮は採用条件としない。C02全体は旧179.784秒から195.934秒、監視あり202.158秒へ悪化した。iteration08では140有効サンプル中Heavy65件、C02 Categoryの完全包含45件すべてHeavyを観測したが、旧基準に同じ監視がなく、温度・他プロセスが遅延原因だとは確定できない。摂氏温度とプロセス別GPU使用率は取得できていない。監視負荷を含む基準値として条件を明記し、監視なしiteration07と混同しない。

C02後段は固定参照groupを注入した比較で、通常経路の意味品質と120秒予算適合は未解決。採用対象は保存済み検証helperと標準ハーネス契約であり、通常経路への再接続・main merge・リリース完了を意味しない。

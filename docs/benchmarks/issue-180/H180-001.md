# Issue #180: 採用済みbaseline H180-001

## 要約

2026-10-19、ユーザーの明示判断により①cacheの一括評価を採用した。次回以降の#180追加改善は、この変更を含むH180-001（旧条件表記D-T）をbaselineとする。元方式（層別評価）へ黙って戻したり、過去baselineを現行baselineとして使用したりしない。

## ハーネスID

| 項目 | 値 |
| --- | --- |
| ハーネスID | `H180-001` |
| 表示名 | KV一括評価採用版 |
| 旧条件表記 | D-T ＋ cache一括評価 |
| 構成を保存したcommit | `89eb61ab` |
| 基準測定 | iteration05 |

`H180`はIssue #180の系列、`001`は構成の連番を表す。今後は「H180-001をbaselineにする」「C01 / H180-001」のように指定する。D-T単独では一括評価の有無を区別できないため、主識別子には使わない。

ハーネスIDは構成を識別し、iterationは測定回を識別する。同じ構成の再測定では`H180-001`を維持し、新しいiterationへ保存する。動作、prompt/入力契約、生成条件、評価方式を変える比較候補には新しいIDを割り当て、IDを再利用して構成を上書きしない。実行ファイルのhashや環境はIDとは別に各実行契約へ記録する。

次回以降の実行契約では実行する構成を`harness_id`、比較元の構成を`baseline_harness_id`として記録する。今回の採用を基にした比較元は`baseline_harness_id: H180-001`とする。

過去の実行契約・raw応答・報告は書き換えない。iteration04とiteration05の一括評価版は同じ構成であり、採用後の呼称はH180-001。元方式を測ったiteration06はH180-001の比較用controlで、H180-001自体の測定ではない。

## 採用した処理と固定条件

- Groupingから同じ計画内でmodel/tokenizerを保持する。
- Category→Textの共通事実入力について実token prefix一致を確認してKVを再利用し、Categoryの思考・回答は継承しない。
- 共通prefixのKV準備で不要なlogitsを評価しない（iteration03の改善を維持）。
- 各chunkのcache評価は`eval(cache)`とする。旧`for entry in cache { eval(entry.state) }`へ戻さない。
- thinking予算はGrouping/Category/Text = 512/384/384（D-T）、seed144、temperature0、topP1、topK0。既存のmodel/revision、prompt、schema、出力/context条件を基準とする。
- chunk512、同期とMemory.clearCache()の頻度、KV snapshot/copy方法は変更しない。②不変grammarデータ保持・③同期/解放頻度の改善は未実施であり、今後はこの状態との差分として扱う。
- eval(cache)はinnerState()を評価する。旧state評価との対象配列表現の差も含んだ採用であり、state配列だけを一括評価する別実装に置き換えたものではない。

採用版の基準値は、環境整備後のiteration05のD-T結果とする。iteration06は元方式の比較用control、iteration03は過去baseline、iteration04は負荷等の変動を含む初回測定として保存し、現行baseline値にはしない。

新baselineの再推論が必要な場合は、その新しい比較の条件・回数・要求上限・停止条件を事前固定する。保存結果を使う場合は過去測定であることを明示する。今回の採用を無制限の追加推論・retry・repair・Gold調整の許可と扱わない。

## 検証結果と限界

元方式を同じ検証環境で再実行したiteration06との比較では、C01の合計はほぼ同じ、C02はKV準備約9.38秒（18.1%）、Category＋Text約15.47秒（12.8%）の短縮を観測した。全6応答の最終JSONは一致し、両ケースの最終Validatorが受理、MLX peakは一致した。各条件1回・逐次測定、helperのビルド時点差があり、一般的な改善率や単独の因果効果を確定した判断ではない。

C02の実Groupingは参照1groupに対して3groupsで、後段は固定参照groupを注入した比較。意味品質課題と通常120秒予算への適合は未解決。検証経路のtimeoutなしはproduction既定120秒の変更を意味しない。

本採用で保存した変更は検証helperのKV経路である。通常経路へD-Tを接続した過去の未commitコードは所在不明で、このcheckoutには含まれていない。今回の採用記録・pushを、通常経路への再接続、mainへのmerge、リリース完了とは扱わない。

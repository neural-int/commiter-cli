# 独立反例検査の設計案（未承認・未実行）

## 判断対象
#155の限定GOを前提にしない探索を#154へ追加する案。現行Bの開始条件は変更していない。実装・新Issue作成・推論・外部コード実行は未着手。

仮説は「LLMの正しい対応付けを前提にしなくても、候補の部分適用で得た具体的な矛盾を、hostが限定的な拒否理由にできる」。最終コミット境界の決定、同一目的の認定、production候補の成立は別の検証である。

## 既存検証との差分
#149 H12の実行結果をLLMへ追加する方式と異なり、実行観測をhostの拒否条件へ直接使う。#150 Cの意味スコア最適化とも異なる。#155のattribution精度を改善したという主張はしない。ただしhost拒否条件だけでは正解選択・独立目的分離を保証しないため、候補包含率と誤棄却を別に測る。

## 最小検査の具体例
1. Divideのゼロ入力修正と対応assertion。修正後assertionだけを旧実装へ適用すると失敗する候補を用意する。実装だけ・テストだけのPASS/FAILから両者の同一目的を断定しない。
2. Labelの空白除去と無関係なログ文言変更。ログを別候補へ置いた状態でも観測条件を満たす例を含める。PASSでログの独立性を認定しない。
3. 共有test内でDivideとLabelを同時に検査する例。片方の失敗だけから、両修正の結合を強制しない。
4. testなしの変更、欠落依存、実行不能、timeout。拒否根拠がない状態はunknownへ分類し、意味成功へ加算しない。
5. 二つの独立変更がそれぞれ完結している候補と、それらを過剰結合した候補が両方PASSする例。観測だけでは区別できないことを必須の反例として保持する。

上記は設計説明用の例であり、独立holdoutではない。新規データを推論前に固定し、使用済み診断と分離する。目的goldはソース・観測から識別可能な範囲に限定し、作者の元commitを正解の十分条件にしない。

## 入力・出力・予算案
入力: lossless ChangeUnit、固定候補集合、適用順序、候補ごとの部分状態hash、before/full-after/controlの観測、明示した実行前提。goldと目的ラベルをruntimeに含めない。
出力: candidate ID、acceptability={contradicted,not_refuted,unknown}、source/observation参照、拒否理由。not_refutedは意味的正解ではない。
候補は一例最大8、実行は一候補につき同じ固定test集合を一回。再試行・候補修復・モデル探索なし。初期host-only検査のモデルcallは0。壁時計は一実行30秒、全検査300秒を上限案とする。既存依存だけを使う。
外部repositoryのコードを実行する場合は、その具体的範囲と隔離方法を先に示して承認を得る。初期設計は外部コードを実行しない。

## 事前判定案
- 明示的矛盾を含む候補をすべて拒否し、対照として成立する候補を一件も誤棄却しない。
- unknownをnot_refutedへ変換しない。source位置・再構築・完全ID・部分状態・予算を全件で検証する。
- 候補に正解が含まれないケース、全候補PASS、過剰結合PASSを別に報告する。
- GOは「限定的な候補拒否能力」のみ。positive/negativeの意味品質、最終partition品質、4ファイル超のproduction品質とは分離する。
- 観測が候補を区別しない、正解候補を拒否する、拒否根拠が実行環境差だけの場合はNO-GO。結果を見てtest・候補・閾値を追加して通過させない。

## 承認された場合の変更範囲
#154へ独立探索として追加し、A→Bの現行統合経路は保持する。既存Bを黙って開始する扱いにしない。必要な新子Issueを起票し、専用worktreeで事前登録と最小検査を行う。#155のNO-GO、#150未達、production4ファイル上限を保持する。

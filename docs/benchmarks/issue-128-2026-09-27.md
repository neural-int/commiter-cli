# Issue #128: candidate relation graph の合成 fixture 計測（2026-09-27）

## 結論

現時点で candidate component を最終 grouping の制約にする pruning rule は採用しない。ラベル付き fixture の正解同一 group pair 8組のうち、edge による component が保持したのは5組だった。`multi_commit` で1組、`large_diff` で2組を落とす。ディレクトリ hint は独立した変更を誤って近づける例もある。

relation context の追加が最終 grouping を安定して改善する証拠もまだない。一方、MLX の24ファイル fixture では全ファイル割当が baseline 0/3、relation 追加後 3/3 となった。この fixture は正解 grouping をラベル付けしていないため、割当成功と grouping 品質を混同しない。既存の補助 context と fallback を維持し、数値閾値や追加 pruning は設定しない。

## 条件と定義

- 比較対象は同一の合成 diff を使った **before**（従来の planning 入力）と **after**（relation context を追加）。入力の違いは relation context と、その省略時の bounded status のみ。出力 JSON schema、renderer、`contextinput.Prepare`、`planning.Generator`、`planning.Validate()` は共通。
- モデルはローカルに保存済みの Ollama `ministral-3:3b-instruct-2512-q4_K_M` と MLX `mlx-community/Ministral-3-3B-Instruct-2512-4bit@a962dcb09eee4169c890e544c9eb938f1113fdee`。MLX helper は Metal smoke が `metal_ok`。モデルの量子化方式は異なる。モデル・依存のダウンロード、cloud API、実 repository の diff は使っていない。
- 実行環境は macOS arm64 / Go 1.27.1 / Ollama 0.33.3。MLX は別のローカル checkout に存在した既存 Release helper を使用し、その SHA-256 は `da8a7c24770047827ec159649254e04554cf50736182d191e634cdfb0fa6ae48`。helper 自体をこのワークツリーで再ビルドしていない点は再現上の制約。
- 1試行の生成上限は1024 token、wall time 上限は2分。各 backend・fixture・arm をまず1回測定した。追加で MLX `many_files` を before/after 各2回（2組目は実行順を逆にした）、Ollama `normal` を各3回（順序を交替）測定した。時間には helper 起動とモデル読み込みを含む。サンプリングによるばらつきがある。
- **edge recall** は、ラベル上同一 commit に属する2 file ID が同一 candidate component に残る割合。**hint recall** は同じ2 file ID が同一の grouped path-proximity hint に現れる割合。hint は component を接続しない。**hit/miss** はラベル上の同一/別 group と relation または hint の整合件数。hard rename は単一 file ID の old/new path が保持されたか別に数える。
- **dense pairs** は `n(n-1)/2`、**candidate pairs** は各 component 内の pair 数の合計。差を pair reduction とする。これは候補空間の診断値であり、planner が component 間の grouping を禁止するという意味ではない。
- `succeeded` は `planning.Validate()` を通った完全割当。`expected grouping` は順序、type、summary を無視した file ID 集合の一致。24ファイルと診断 fixture は正解 grouping をラベル付けしていない。

ラベル付きの正解 pair は合計8組で、edge recall は **5/8**、hint recall は **4/8**。出力された soft edge 5件はすべてラベル上同一 group（hit 5、miss 0）。同一ディレクトリ hint には、同一 group pair の hit 4件に対して別 group pair の miss 3件があった。`same_directory_independent` の1件は hint として残るが edge にはならない。

診断 fixture では ambiguous / unresolved / unsupported が各1件で、確定 edge は0件。交差ディレクトリ fixture では direct import edge が1件、test path の未解決観測が1件。追加の Git rename fixture では hard relation の保持が1/1、miss 0。rename は単一 node の属性になり、edge・hint・観測が空なので planning の relation context は `ineffective` として省略された。

前処理を同一プロセスで各20回測った中央値は、before が fixture 別で0.010–0.039 ms、after が0.013–0.087 ms。Tree-sitter 初期化などの冷状態を含まない値であり、実 repository の処理時間は示さない。

## 再現手順と検証

`codex/issue-128` の `tools/benchmark110` に追加した `-compare-relations` を使う。prompt と生成文は保存せず、標準出力は数値、file ID、検証結果、違反コードのみを JSONL で出す。

```sh
GOCACHE=/tmp/commiter-issue128-gocache go run ./tools/benchmark110 -compare-relations -describe -fixture all -repeats 20
GOCACHE=/tmp/commiter-issue128-gocache go run ./tools/benchmark110 -compare-relations -backend ollama -ollama-model ministral-3:3b-instruct-2512-q4_K_M -fixture all -repeats 1 -timeout 2m
GOCACHE=/tmp/commiter-issue128-gocache go run ./tools/benchmark110 -compare-relations -backend mlx -mlx-repo mlx-community/Ministral-3-3B-Instruct-2512-4bit -mlx-revision a962dcb09eee4169c890e544c9eb938f1113fdee -helper /absolute/path/to/commiter-mlx-helper -fixture all -repeats 1 -timeout 2m
```

反復は各コマンドの `-fixture normal` または `-fixture many_files` と `-repeats 2` / `3` で実行した。`go test ./...`、`go vet ./...`、`git diff --check` は成功。テストには `httptest` 用 localhost 待受が必要で、計測用 Ollama サーバーは全テスト前に停止した。SRS の日英版は今回仕様を変更していないため更新していない。

## 判断と残るリスク

- **pruning:** `multi_commit` と `large_diff` の正解 pair が component をまたぐ。これを除外する rule は既定で有効化しない。削減率だけから threshold は定めない。
- **relation context:** MLX 24ファイルの完全割当には改善の兆候があるが、ラベル付き grouping の改善は確認できなかった。既存の補助 context と fallback を維持する。
- **追加測定:** fixture を増やし、複数 seed / 反復で grouping 品質を評価するまでは production 品質ゲートを決めない。現結果は合成データ、固定版3Bモデル、2分上限に限る。

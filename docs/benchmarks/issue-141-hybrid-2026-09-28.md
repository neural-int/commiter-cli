# Issue #141: relation seed と file-centric 割当の比較結果（2026-09-28）

## 結論

benchmark 内で `source_test` と `direct_import` の soft edge を unit 縮約に使うと、今回の6 fixture では file-centric より false split が減った。`source_test` は16→8 pair、`source_test + direct_import` は16→6 pairで、exact grouping は4/12→6/12→8/12。全条件の完全割当は12/12、false merge は0だった。ただし[事前登録](issue-141-hybrid-preregistered-2026-09-28.md)した反例では、どちらの edge も異なる変更目的を強制結合し得る。さらに正解 grouping の Pass 2 は一部で `invalid_metadata_groups` となり、最終成功は2/12、4/12にとどまった。**この結果は hybrid の追加検討には値するが、soft edge の無条件 must-link や production 採用を認めるものではない。**

## 条件と安全境界

推論前に条件とコードをコミット `3e6f383` で固定した。前回と同じ6 fixture・正解 group・repository input / relation context、ローカル MLX model `mlx-community/Ministral-3-3B-Instruct-2512-4bit@a962dcb09eee4169c890e544c9eb938f1113fdee`、helper SHA-256 `da8a7c24770047827ec159649254e04554cf50736182d191e634cdfb0fa6ae48`、1024 output token/request、2分/plan、2反復を使った。`file-centric`、`hybrid-source-test`、`hybrid-source-test-import` の36試行を同じ実行内で測り、2巡目は arm 順を逆にした。追加モデル・依存・クラウド API は使っていない。

seed は既存 extractor の `Soft` edge の kind と reason から決め、正解 group を参照しない。candidate component、同一ディレクトリ hint、changed identifier、未解決・曖昧な観測は使わない。Go は unit の全 ID を検証してから元の file ID へ展開する。Pass 1 が完全割当かつ正解 grouping の場合だけ、前回と同じ batch Pass 2 を実行した。structural failure には最大1回の repair を許す。prompt と schema も unit 表示に合わせて変わるため、観測した差を seed 単体の因果効果とは言えない。

## 主比較

false merge / false split は正解と異なる / 同じ file pair の誤結合 / 誤分割の合計。すべての試行が構造的に有効だったため、pair 指標は36試行すべてで採点可能。`exact + metadata` は正解 Pass 1 の後に Pass 2 が元の group に対応し、`planning.Validate()` を通った件数である。

| 条件 | 完全割当 | exact grouping | false merge | false split | per-file accuracy | exact + metadata | calls | wall 合計 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| file-centric | 12/12 | 4/12 | 0 | 16 | 64/78 | 0/12 | 16 | 230.0s |
| hybrid-source-test | 12/12 | 6/12 | 0 | 8 | 72/78 | 2/12 | 18 | 236.6s |
| hybrid-source-test-import | 12/12 | 8/12 | 0 | 6 | 74/78 | 4/12 | 20 | 248.3s |

| fixture | file-centric exact / split | source-test exact / split | source-test-import exact / split | seed edge 件数：source-test / 追加 import | hybrid で残る問題 |
| --- | ---: | ---: | ---: | ---: | --- |
| multi_commit | 0/2・4 | 0/2・2 | 0/2・2 | 1 / 0 | README と docs の結合を seed で表せない |
| cross_directory | 0/2・2 | 0/2・2 | 2/2・0 | 0 / 1 | source-test 単独では import を使えない |
| same_directory_independent | 2/2・0 | 2/2・0 | 2/2・0 | 0 / 0 | seed がないため差を seed に帰属できない |
| mixed_24 | 2/2・0 | 2/2・0 | 2/2・0 | 0 / 0 | seed はなく、Pass 2 が失敗 |
| holdout_split | 0/2・4 | 2/2・0 | 2/2・0 | 2 / 0 | Pass 2 が失敗 |
| holdout_join | 0/2・6 | 0/2・4 | 0/2・4 | 1 / 0 | implementation / test 以外の docs を分離 |

6 fixture 内の seed は source-test で8 edge、import 追加後は10 edge（2反復合計）。強制した正解 pair は8→10、強制した false pair はいずれも0。これは今回の labeled fixture に限る。`multi_commit` と `holdout_join` の残余 false split は、seed だけでは docs を同じ変更目的へ結び付けられないことを示す。`same_directory_independent` と `mixed_24` では seed が0で、hybrid と file-centric の差が出れば unit 表示・指示など別要因である。今回は両 fixture の grouping は全条件で同じだった。

## seed の反例と Pass 2

事前に用意した2つの guardrail fixture では、既存 extractor が実際に soft edge を作る一方、正解 group は別である。

| guardrail | 観測された edge | 縮約が強制する false merge |
| --- | --- | ---: |
| 同名 source/test が別の変更目的 | `source_test` | 1 pair |
| 別目的の変更 file が shared JS を import | `direct_import` | 1 pair |

これは source/test 命名や import の関係が実在しても、同じコミットにすべきことまでは保証しない反例である。guardrail は推論せず seed 選択の決定的検証だけを行い、主比較の分母に含めていない。production で無条件に hard merge する案はこの時点で満たせない。

Pass 2 は file-centric で正解 grouping 4件中0件、source-test で6件中2件、source-test-import で8件中4件成功した。失敗は各条件4件の `invalid_metadata_groups` で、`mixed_24` と `holdout_split` の正解 grouping に集中した。生の metadata 応答は保存していない。この failure code は metadata 件数、group ID の重複・欠落、`breaking` 欠落をまとめるため、詳細原因は特定できない。`same_directory_independent` は seed が0でも hybrid 条件の Pass 2 が成功した。前回 oracle の per-group 4/4成功を、今回 batch Pass 2 の成功保証とは扱わない。

Pass 1 初回 calls は各条件12、repair・transport retry は0。Pass 2 calls は4 / 6 / 8で総 calls の差を説明する。すべての request の stop reason は `completed`。backend は output token count を返さず、記録値は `unavailable`。入力・出力 bytes と wall は次のとおり。

| 条件 | Pass 1 入力 | Pass 2 入力 | 出力 | 最大 plan wall |
| --- | ---: | ---: | ---: | ---: |
| file-centric | 66,738 B | 32,672 B | 4,472 B | 82.2s |
| hybrid-source-test | 68,368 B | 41,002 B | 5,128 B | 74.0s |
| hybrid-source-test-import | 68,168 B | 46,340 B | 5,816 B | 73.2s |

入力 bytes は実 token 数ではない。hybrid の wall 増加には、正解 grouping が増えて Pass 2 を実行した件数も含まれる。wall の小差を性能差とは判断しない。

## 前回との照合と判断

今回の file-centric は[前回の同条件の12試行](issue-141-file-centric-2026-09-28.md)と、対応する全試行で初回 prompt bytes、完全割当、grouping、failure、calls が一致した。wall は前回201.6秒、今回は230.0秒と変動した。したがって grouping と failure 分類は比較可能だが、少数反復の所要時間差を改善・悪化の確証としない。

主比較では hybrid が false split を減らしたため、edge 由来の unit 化が有効になり得ることは確認できた。ただし6 fixture の0 false merge を一般化できず、guardrail は hard 縮約の反例である。Pass 2 も end-to-end の制約として残る。現時点では production planner / SRS / 通常 CLI を変更しない。次に進むなら、(1) seed を hard にせず解除可能な候補として扱う案で誤結合の guardrail を含む評価、(2) 固定 group label と同じ batch/per-group 条件による Pass 2 単独診断、を別々に事前登録する。pairwise / local boundary classification へ移る判断は、この小規模検証だけでは確定しない。

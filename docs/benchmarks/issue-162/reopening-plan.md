# 拡張必須を前提にした打開策の設計案

ユーザーは4file構成を実用要件未達と位置付け、拡張を絶対要件と明示した。候補探索の保留を製品の着地点にしない。変更内容を先に言語化して意味類似度で判断する方式は不採用。既存の構造検証と局所/全体判断の失敗は保持する。

## 優先する構成

原diffと必要な未変更コード → ローカルの全体分割専用エンジン → file membership計画 → 機械側の完全割当・依存順・Git安全検証 → 確定groupごとの既存metadata生成。

分割とmetadataに同じ小型モデルを必須としない。分割エンジンは16file全体を同時に判断する。4file windowの連結、LLM要約、類似度のhard-link化、test PASSから独立性を確定する経路は設けない。機械側は入力source ownership、計画整合とGit安全のauthorityであり、意味の正しさを保証しない。容量/時間制約は品質とは別に測る。

第一候補は、現行より強い別のローカルcode/reasoning engineを分割専用に置くこと。新モデルなら実行前にhardware/runtime/revision/容量/生成契約を固定する。現行Qwen3-8Bの予算増加だけを新能力と呼ばない。モデル名・サイズ・公開benchmarkだけではこの用途の資格を認めない。

第二候補は、commit分割に特化した学習済みローカルplanner。これは既存pair-score/solverの再実装ではなく、独立性と共同レビューの判断能力を学習で追加する仮説。第一候補の対照から入力内の根拠で判断が成立する条件を先に確認する。単なる過去commit境界を唯一の正解として大量学習しない。

## 最初に確定すること

1. 少数の未使用・根拠を監査したケースで、既存エンジンと新エンジンに同じsource・判断課題・許容partitionを提示する。独立変更、補償変更、対応実装/test、cross-file単一変更を正負対照に含め、順序反転も測る。過去failuresは再現診断、未使用ケースは資格判定と区別。
2. 最初から大規模にarchitecture/model/taskの直積探索をしない。比較対象は既存1、新候補1。具体的な入力hash・model/runtime・予算・call数・Gateはモデル資源監査後に別の事前登録で固定し、推論前にcommit/pushする。この文書は実験事前登録ではない。
3. 根拠十分な局所正負で新エンジンが改善しなければ全体構成を作らない。入力から識別不能な目的はモデル能力不足と混同せず別集計。必要に応じて根拠または課題定義の問題へ戻る。
4. 局所資格が成立した場合は、同じ対照構成で8/16fileを直接判断させる。全体で崩れるならcontext/global assignmentの課題と記録し、局所成功を16file成功にしない。
5. 全体成立後にmetadataを統合し、未知評価・確定計画・費用・4file回帰を検証。ここまで成立して初めてproduction candidate。既存基準を事後に緩和しない。

## 学習へ進む条件

新エンジンが同じ入力で解け、小型エンジンが解けない境界が確認できた場合、能力差を小型へ学習する仮説を検討する。原diffとsourceを入力、確定file membershipを出力とする。説明文を中間表現にしない。レビューラベルは人間による根拠監査と複数許容partitionを反映し、teacher出力そのものを正解としない。repository/変更familyで学習・評価を分離し、同一履歴や近似変種をholdoutへ混入させない。品質・提示順・誤統合/誤分割・保留・資源を別測定する。学習データ件数や成功率は未確定であり、現時点の実績ではない。

## 現在の実行境界

設計案の保存のみ。新モデル取得・依存追加・推論・学習・production変更は未実行。ユーザーの拡張必須条件を満たすための再開方針であり、実現の保証や過去NO-GOの取消ではない。次は新ローカルエンジン1候補の資源適合性と実験契約を準備する。

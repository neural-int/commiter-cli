# H184-004 invalid_scopeのハーネス分析

保存済みText入力・wire・出力・Go overlayと最終validatorを追跡した。両群ともREADMEグループのscope=docsが直接の拒否原因。Text入力のtype=docsと出力scopeを混同している可能性はあるが、モデル内部の原因は未確定。

確定事項は、生成Schemaがscopeを1〜16文字の文字列として許す一方、最終validatorは全commit typeと同名のscopeを拒否すること。生成制約は最終受理条件より弱い。禁止指示は実systemへ届いており、生成例は無効化されていた。docsは生のhelper応答に存在し、Go側はscopeをそのまま最終Planへ転記する。ホストによる値の上書きやtype/scopeの取り違えは見つからない。

保存済み実応答を使った非推論Go診断で、両群とも元のPlanはinvalid_scope、診断用コピーのdocsだけをreadmeへ変えると違反0となった。元出力・測定スコアは変更していない。意味上の要約品質まで正しいという意味ではない。

scope=docs拒否は既存の単体テストにも明示されており、偶発的なvalidator誤動作ではなく意図した製品規則。改善方針は、この禁止を維持するかの仕様確認を先に行い、維持する場合はモデルへ渡すSchema/文法と最終規則の整合を検討すること。対応するJSON Schema演算子のランタイム対応確認が必要。単に禁止指示を強めること、モデル品質だけを原因とすること、診断用置換を本番補正へ流用することは今回実施していない。

追加モデル生成0、製品変更0。安全性検査のJWT誤検出とは別の問題。実験上の次の変更を採用したものではない。

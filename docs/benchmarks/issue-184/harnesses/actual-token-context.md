# Harness 004 revision 3：実token判定と12K境界

3-Phaseのコンテキスト枠を全フェーズ65,536 tokensへ固定する。Groupingで小さい枠を選び、その枠をCategory／Textへ引き継ぐ処理を削除した。各フェーズの出力予約4,096 tokensを含めて上限を検査するため、最終入力は最大61,440 tokensとなる。

| 条件 | 動作 |
|---|---|
| 実入力が12,000 tokens以下 | 毎chunkに追加していたGPU待機・未使用allocator cache解放を省く |
| 実入力が12,000 tokens超 | 従来の毎chunk同期・未使用allocator cache解放を行う |
| 入力＋出力予約が65,536以下 | 生成可能 |
| 必須入力＋出力予約が65,536超 | 生成せずErrTooLargeで停止 |
| 任意の履歴候補が上限を超える | 当該最終応答の記録全体を省略 |
| 計数自体が失敗 | 0 tokens扱いや黙った履歴省略をせず停止 |

12Kは12,288ではなく**12,000**を指す。12,000ちょうどは軽量側、12,001は保護側。以前の実入力12,284 tokensの条件は保護側になる。12,000が最適な境界であることや、速度改善は、この実装だけでは証明されない。

## 最終入力と計数の一致

各フェーズは生成要求を1回だけ送る。計数専用のIPCと`CountOnly` APIは削除した。helperが通常の入力準備で得た実token数を上限判定に使い、その**同じLMInput**を文法制約・prefill・生成へ渡す。最終入力のchat template適用・tokenizeを生成前にやり直さない。UTF-8バイト数によるtoken推定へ戻す変更でもない。

Goは安全性・重複排除・保持バイト上限の検査を行い、任意履歴を差分とは別の表示断片として1要求に収録する。大きい差分本文は一回だけ送る。helperで断片を結合した全文は、従来のLLM表示と一致する。外側IPCは正規JSONを維持する。

履歴の採否は**全件を含む最終入力が収まれば一括採用し、超過時だけ回数を制限した一括選別**を行う。通常の準備は1回のまま維持する。超過時は次の手順とする。

1. 履歴なしの必須入力を準備し、出力予約込みで正確に検証する。収まらなければ`input_too_large`で停止する。必須入力が60,000 tokensを超えたことだけでは拒否しない。例えば61,000なら履歴に使える残りは440 tokensある。
2. 全件入力と必須入力の実token数の差、および履歴各件のUTF-8バイト数から、候補選別用のバイト予算を比例推定する。ホストの既存の優先順で記録全体を選び、予算に入らないものは飛ばす。固定のbytes/token値や推定値で64Kへの収容を確定しない。
3. 選んだ候補を正確に準備する。出力予約込みで収まれば、その同じ`LMInput`を生成に使う。超過なら、直前の実計測に基づく推定と「選択バイト数の半分」の小さい方へ予算を減らし、再選別する。差分や履歴本文の途中を切り詰めない。
4. 候補の準備は最大3回。候補がなくなった場合や上限まで収まらない場合は、手順1で検証済みの履歴なし`LMInput`を再利用する。最後に履歴なし入力を作り直さない。

したがって全入力準備は**通常1回、超過時も最大5回（全件1＋必須1＋候補最大3）**。履歴件数に依存して候補を1件ずつtokenizeする処理を削除した。候補の走査そのものは件数に応じて行うが、重いtemplate適用・tokenizeの回数は固定上限を持つ。tokenizerや入力形式自体の失敗は履歴省略に置き換えず停止する。

この方式は、履歴の最大保持を保証しない。推定による採用漏れを許容し、必須Git差分・厳密な上限・処理回数の予測可能性を優先する。必須差分の削減、追加の計数IPC、採用済み最終入力の再tokenizeは行わない。

応答には採用した履歴の元インデックスを返す。Goは範囲・順序・重複を検証し、Groupingで実際に使った履歴をTextの共有データへ固定する。Categoryは独立入力で判定する。文法制約・64K/4096・12,000境界は維持する。

`inputPreparationCalls`は各phaseの全入力を準備した回数を記録する。通常は1。共通prefix境界を特定するための別の入力の準備は既存どおり残すため、プロセス全体のtokenizer呼出し回数を1と主張するものではない。

保護判定には、キャッシュ再利用で省いたsuffixだけではなく**再利用するprefixを含む全入力**を使う。Groupingの手動prefix準備と通常のprefillの両方へ同じ判定を適用する。prefix状態を確定させるための`eval(cache)`と、必要なKVコピーは保持する。

## 範囲

通常3-Phaseの4ファイル上限、サイクル120秒、summary48文字、各phase出力4096、Thinking OFF、文法制約、native KV、sampling／seed、型別prefix再利用を維持する。既存の`llm.context`／`llm.max_context_tokens`による段階選択は旧single-pass経路だけに残し、3-Phaseの枠選択へ使わない。

GoのIPC最大1MiB、応答4MiB、履歴の保持バイト上限は資源制限として維持する。コンテキストtoken推定とは別の制限である。通常3-Phaseの前で旧Prepareが行っていたバイト予算による拒否・縮約は迂回する。旧Renderer・制約オブジェクト自体の撤去、履歴取得の統一、旧Planner廃止は[Issue #187](https://github.com/neural-int/commiter-cli/issues/187)の別スコープとする。

## 検証

- Go：64K固定、64KiBを超える表示でも実token数で受理、後段30K入力、61,440／61,441境界、任意履歴の採否、計数失敗時停止、Grouping／Text共有データ不変。
- Go–helper：履歴の採否を含めてもIPCは全3phaseで3要求だけ。差分を一度だけ送信し、実改行表示・ホスト元データを維持する。履歴選択応答の欠落・不正インデックスを拒否し、Grouping/Textで一致させる。
- Swift：11,999／12,000／12,001／12,284の保護境界、64K内の4,096出力予約を検査する。

これらの構造検査と、速度比較・多ファイル意味品質の再評価は別である。

### 初回の計数専用IPC版の確認結果（2026-11-03・旧実装）

Swift Release helperで、保存済みのSHA固定モデルを使った公開合成1ファイルの疎通を各1回実行した。App Serverや実Gitリポジトリへの書き込みは行っていない。計数結果は、生成時にhelperが計測した全入力token数と全phaseで一致した。

経過時間はテスト本体の観測値であり、順序・冷却・反復を揃えた性能比較ではない。短い合成入力での疎通であり、12K付近の実入力におけるメモリ安全性・短縮効果や、保存7/9/11ファイルfixtureの意味品質を新たに実証したものではない。

Swiftの既存57件に加え、今回の境界・出力予約2件が成功した。初回の既定SwiftPMビルドは、このMacのMetal Toolchain未導入で失敗した。依存の固定revisionは変更せず、SwiftPM nativeによるReleaseビルドと同じ固定依存用の既存Metalライブラリで全テストと上記疎通を実行した。追加依存やCI設定変更、CI成功の主張はない。

最終状態で`go test ./...`、`go vet ./...`、CLIのビルド、`git diff --check`が成功した。旧benchmark146のmock／oracle／templateアダプターにも計数インターフェースを接続し、実測バックエンドでは実計数を必須にした。合成値を実測token数として記録しない。新しいRelease helperをローカルの`dist`にも配置した。ソースのcommit／push、PR更新、mainへのマージ、製品リリースはこの作業では行っていない。


### P2修正：計数専用IPCを削除

初回の上記実装は事前計数と生成で準備を繰り返していたため、現行仕様としては採用しない。上記の初回観測値を現行の性能結果として流用しない。Swiftの追加テストでは、全件採用時に準備1回、超過時の順序付き選択、採用した準備済みオブジェクトの同一性、必須入力超過・tokenizer失敗時の停止を確認する。

P2修正後、Go全体テスト・go vet・差分チェックが成功。Swift ReleaseビルドとSwiftの61件＋XCTest 2件（合計63件）が成功した。公開合成1ファイルと安全な最終応答1件を用い、モデルを追加取得せず各1回疎通した結果は以下のとおり。

| モデル | Grouping入力／準備回数 | Category入力／準備回数 | Text入力／準備回数 | Text再利用tokens | 最終validator | テスト本体経過 |
|---|---:|---:|---:|---:|---|---:|
| Qwen3.5-4B 4bit | 868／1 | 837／1 | 836／1 | 326 | 受理 | 14.02秒 |
| Gemma E4B 4bit | 890／1 | 863／1 | 858／1 | 338 | 受理 | 11.98秒 |

初回版の表とは履歴を含む入力が異なるため、上記時間を速度改善率の算出には使わない。今回の確認結果は、計数専用IPCゼロ・全phaseの全入力準備1回・prefix再利用と最終validatorの接続である。12K近傍や多ファイルの性能・意味品質の再比較は実施していない。


### 履歴超過時の一括選別・回数制限

修正前は、履歴100件がすべて収まらないテストで全入力準備102回を再現した。今回、通常の全件一括採用は維持し、超過時だけ上記の最大5回へ変更した。再現ログ・修正後のテスト結果はprivateに保持する。旧方式の正確な1件単位採否と新しい推定選別は同一条件ではないため、以前の履歴保持率・意味品質を新方式の結果として扱わない。

修正後の合成テストでは、履歴20件・100件・2,000件がすべて収まらない場合でも準備5回、履歴なし入力の準備は一度だけだった。全件収容時は1回、必須入力が上限ちょうどなら2回で確認済み必須入力を再利用する。61,000 tokensの必須入力に対して残り440 tokensへ履歴を収め、出力予約込み65,536ちょうどで受理するケースも成功した。推定が外れた候補の一括削減、採用した準備済みオブジェクトの同一性、tokenizer失敗の伝播も確認した。

Swift Releaseビルド、Swift Testing 67件＋XCTest 2件（合計69件）、Go全体テスト、差分チェックが成功。Qwen/Gemmaの公開合成入力による各1回の疎通結果は次のとおり。両方ともGrouping/Category/Textの全入力準備は各1回、prefix再利用・最終validatorも通過した。

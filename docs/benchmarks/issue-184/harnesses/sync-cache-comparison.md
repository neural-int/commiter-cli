# 同期を維持したキャッシュ解放の切り分け

状態: 本測定2回が正常終了。監視エラーなし。追加の逆順2回は実行しない。

## 条件

前回の固定20,475 tokensのGrouping要求を使用。Qwen3.5-4B 4bit・Thinking OFF・grammarあり・native KV・入力上限65,536・出力上限4,096・seed144。両条件の要求hashは一致し、同じ新しいRelease helperを使用。毎chunk同期ONを維持し、未使用バッファのキャッシュ解放のみON/OFFにした。prefix再利用なし、各要求は新規helper。通常設定は変更しない。

同一の短入力による両条件のウォームアップは集計対象外。各実行前にnominal・低電力OFF・負荷とメモリの開始条件を60秒維持。最大4回の承認範囲で、まず2回の結果から判断した。

## 解釈と限界

同期を維持しても、解放を外すと以前の全面OFFと同様の大きな割り当て・圧縮・swap増加が現れた。同期を外したことだけでこのメモリ挙動が発生した、という説明では足りず、明示的な解放の有無が重要だったことを支持する。

GPU指標はAGXAccelerator全体でありhelper専用の常駐メモリではない。圧縮とswapoutはOS全体の累積カウンター増分であり、物理I/O量やhelperのデータ量とは扱わない。監視区間は要求全体でありprefillだけに限定していない。背景負荷や生成中の熱変化を排除した実験ではなく、何秒が圧縮・I/O・熱に由来するかは未特定。

今回も合成的に長くしたGrouping入力だけの診断であり、3フェーズE2E・自然な長入力の精度・最適な解放頻度は未検証。

## 準備時の失敗と修正

初回の既定ビルド経路はMetal Toolchain欠落で失敗。新規依存を追加せずnativeビルドと既存の固定metallibへ切り替え、Releaseビルドとmetal_okを確認した。

初回ウォームアップで、diagnostic-sync-onlyが短入力では同期OFFになる条件不整合を検出。本測定0回で停止し原本を保持。同期条件をlegacyと揃えた新しいReleaseで、別の原本ディレクトリへ最初から固定し直した。修正後は短入力ウォームアップと20K本測定の両方で同期ONを確認した。未完了の準備実行を今回の2回へ数えない。

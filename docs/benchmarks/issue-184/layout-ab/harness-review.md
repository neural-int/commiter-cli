# layout-ab 誤分類に関するハーネス監査

## 結論

Categoryのfeat→testは観測事実だが、共通情報を先頭へ置いたこと単独の効果とは判定できない。探索ハーネスがrole、情報の局所性、参照方法、メッセージ境界、serialize表記を同時に変えた。特に分類規則のsystemからuserへの移動と、グループ内差分の共有辞書への分離は誤分類を誘発する候補。

## 確認した事実

- 全3phaseで、共有filesをfile_idで解決しhistoryを戻すと、元payloadの全フィールド・全値と一致した。Git差分、履歴、照合状態、group membershipの欠落や取り違えは検出されなかった。
- 元system指示はSchema説明を含め、探索案の最後のuser本文にそのまま含まれる。出力Schemaおよびmessages以外の全要求設定も両群一致。
- `test for test-only changes`、`feat for new observable behavior`は削除されていない。ただし探索案ではsystemに存在しない。
- 現行はsystem/userの2メッセージ。探索案は短い共通system、共有データuser、phase指示と入力userの3メッセージ。
- 探索案CategoryのG002はF2/F4を参照する。共有側ではF2がUI実装、F4が対応テストで、間に独立したメール実装F3が並ぶ。元Category入力ではG002.files内にF2とF4の完全な差分が隣接して存在した。
- Groupingは両群同じ正解分割であり、Categoryは固定済み同じグループを受け取った。Groupingの誤りの伝播ではない。
- KV prefix再利用はなく、出力は完了したJSON。Schemaはtestを正当な値として許容するため、意味的な誤分類を拒否しない。

## 誤分類を誘発し得る変更

1. 分類規則がsystemからuserへ移った。ルールそのものはあるが、命令階層を保持していない。役割の変化が出力分布へ影響した可能性がある。
2. G002の本文から実装差分とテスト差分が消え、file_id参照だけになった。分類する時点で別メッセージの共有辞書を結合して読む負荷が加わる。テストに注目して実装の新規挙動を十分に参照しない可能性がある。
3. 共有filesの全体順序はF1/F2/F3/F4/F5。元のCategoryにあった同一グループ内の隣接性が失われた。
4. 追加した共通systemの`File references resolve to the shared evidence`は一般的な参照説明に留まる。各group内の全file_idを解決して実装とテストをまとめて分類する手順を明示していない。
5. user/userというメッセージ境界、HTML escape等のserialize表記も変わった。テンプレートが処理できなかった証拠はないが、順序のみの比較へ混ぜない方がよい。

これらは原因候補であり、単一試行の出力からどれが直接原因かは確定できない。データの機械的欠落とは区別する。

## 次の比較案

共通systemに分類の一般規則（feat/fix/test等）と信頼境界を保持し、phaseの選択・Schema等だけを後半へ置く。参照方式を使う場合も、各グループの全file_idを解決し実装と対応テストを一体として読む規則を明示する。特定fixtureの正解typeを教えない。

役割保持と参照方式の変更を同時に評価せず、まずsystem分類規則の保持だけを変えた条件を現行探索案と比較する。その後、本文の埋め込み/参照を比較する。これは提案であり、追加推論やコード修正は今回実行していない。

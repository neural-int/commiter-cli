# 履歴取得の重複検出とメモリ保護

## Goal

承認されたTurn単位の並列取得を、重複証拠を増やさず、段階的なメモリ保護の下で比較できる研究PoCにする。

## Result / Decision

2/4/8並列の選択、queue登録前のTurn重複検出、item重複検出、同じIDの内容競合検出、v2投影直前の証拠重複検査、所有プロセス群のRSS/圧迫状態による割り当て制御を実装。本番CLI/Collector/Plannerの経路と既定paged100は変更しない。今回の作業は実装とfixture検証までで、新しい実履歴速度測定や最適並列数の決定はしていない。600MBの合計入力予約は今回追加しない。

## Contract

Turnキーはthread+Turn、itemキーはthread+Turn+item、操作キーはthread+Turn+item+change index。同じキーと採用フィールドが同じなら一度だけ保持する。同じキーの内容競合は履歴解析エラーとし、競合Turnを確定証拠として保持しない。異なるキーの同じ本文は独立候補。完了順によらず列挙順へ戻す。

RSSはPoC本体と所有App Server群・子孫の合計。開始前と500ms間隔で監視する。1GiBで増加停止、1.5GiBで新規Turn割り当て停止、1GiB未満かつ正常圧迫状態を2サンプル確認して再開する。1.5GiB到達後の最大並列は指定値の半分（最低1）。2GiB/criticalで中断。監視不能と30秒の停止継続も原因別に中断する。実行中の巨大応答を1.5GiB時点で破棄する方式ではなく、2GiB/critical時にキャンセルする。1応答300MB上限は維持。

## Validation

非空の6Turn×104itemで逐次と2/4/8並列の編集操作・依頼/応答・順序・照合結果が一致すること、要求が同時に重なることを確認する。8並列のfixtureはTurnが6件のため実際の最大同時要求は6。

同一Turn/itemの重複、ページをまたぐitem重複、同一キーの内容競合、競合時の他の完了Turn保持、投影前の重複排除と競合拒否、キャンセルの不完全判定を検証する。メモリ値を注入して増加停止/一時停止/回復/2GiB/critical/監視不能/回復待ち失敗を確認し、2GiB到達時にTurnが新規割り当てされないことも取得経路で検証する。

関連3パッケージの`go test`、並列・重複・メモリ保護の`go test -race`、PoCの`go vet`、研究バイナリのビルドが成功。実履歴を取得するopt-inテストは実行していない。

## Limits / Next gate

RSSは500msのサンプリングでありハードなメモリ割り当て上限ではない。macOSの監視不能時は失敗として返す。並列化や監視自体の速度効果、巨大応答時の実RSS、最適並列数は今回未測定。過去の測定原本は変更しない。新たな依存追加・LLMへの送信・実履歴の追加取得・commit/push・Issue投稿は今回行わない。

## 実測比較（追加実行）

同じ保存Git入力・期間・現在worktreeの対象履歴で、逐次→2→4→8の順に各1回実行した。全セルcomplete、87thread・443Turn・15,097itemで、保持証拠・照合結果は一致。対象編集操作は全て0件のため実編集の照合精度は評価していない。

|指定|取得秒|要求数|受信bytes|実最大同時Turn|
|---|---:|---:|---:|---:|
|paged100|12.946|606|42101220|未監視|
|parallel100|27.869|1049|42283602|1|
|parallel100x4|27.156|1049|42283602|1|
|parallel100x8|25.598|1049|42283602|1|

並列3セルは全監視サンプルでpressure=2。1GiB未満でも警告時の増加停止・接続終了が働き、実最大同時Turnは1だった。各Turn後の接続再生成で要求数が増え、並列指定側が遅くなった。現状の保護下での実測結果であり、2/4/8の真の並列速度比較は成立していない。保護は解除せず、追加再試行は行わない。逐次セルのRSSはこの測定では未監視なのでメモリ量の直接比較はできない。

原本は私有tmpのissue182-parallel-safety-10に保存。公開用summaryには本文・ID・個人pathを含めない。既定paged100を維持し、警告状態でも毎Turn接続を再生成する制御は今後の改善対象とする。

## 警告時の接続再利用修正

前回実測の再起動増加を受け、1GiB以上またはpressure=2では接続を閉じず、Turnの割り当て数だけを制限するよう修正した。接続はworkerごとに再利用するため、同時取得が1でも接続保持数が1になるとは限らない。1.5GiB以上の停止時には取得完了後の接続を閉じて回復を待ち、2GiB/critical/監視不能等の中断は維持する。

6Turn・最大4workerのfixtureで、pressure=2とRSS=1GiBをそれぞれ固定し、実同時Turn数1・操作6件・complete・要求20回を確認。内訳は一覧4回、worker初期化4回、itemページ12回であり、Turnごとに6回初期化した場合の22回にならない。1.5GiB時には接続終了判定が維持されることも確認。実履歴速度の再測定は今回の修正には含めない。

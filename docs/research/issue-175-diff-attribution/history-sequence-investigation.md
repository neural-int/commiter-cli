# 保存履歴の連続編集候補の再調査

ユーザー指示に従いGit差分への帰属は行わず、保存履歴内の依頼・編集列・最終応答の共存だけを調査。

通常checkoutに対応する最初のthreadをApp Serverの読み取りAPIで取得。5秒/受信4MiB枠を維持し、約3.31秒で受信上限に到達。62turnを観測、完了編集イベント30件。全履歴網羅ではなく途中までの便宜標本。

同一pathへの反復編集候補は6件。1turn内6回、1turn内5回、2turnにまたがる4回、2turnにまたがる3回、1turn内2回が2件。各候補に対応するturnには非空のユーザーtextとfinal_answerが残る。同一turn内はAPIのitem順、turn間はstartedAtで並べた。依頼の内容と編集の意味的な対応までは今回判定していない。同一threadの最初と最後だけでなく編集を含むturnごとに依頼と最終応答を追える候補。

各編集diffから追加/削除行を抽出して隣接編集間の完全一致を試すと、今回の候補では一致0。これは単純な比較の結果で、連続性や復元可能性がない証拠ではない。複数hunk、追加後の部分編集、離れた箇所の変更を合成していないため。取消しの確証例も未確認。

判明したことは実際の履歴に反復編集の中間記録と依頼/最終応答が共存すること。全中間ファイルsnapshotが保存されること、欠落なく復元できること、現在のGit変更への帰属が正しいことは未証明。今はGitを照合せず、人工ケース追加もしていない。本文・path・thread/turn ID・秘密値は成果物へ保存しない。実装はopt-inの研究用testのみで本番Collector/Plannerは未変更。

集計はhistory-sequence-candidates.json。実行はCOMMITER_CODEX_SEQUENCE_PROBE=1と明示した対象rootでTestSavedHistorySequenceProbeを起動。通常のgo testではskip。今回probe自体は成功したが受信上限による部分結果を完全取得と混同しない。

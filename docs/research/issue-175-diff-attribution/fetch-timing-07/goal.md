# paged100の取得時間内訳

## Goal

100件方式の起動/初期化、要求送信、応答待ち・受信、JSON解析、path/安全性検証/抽出を分けて記録し、一度実測する。本文・内部ID・cursorはログに含めない。

## Result / Decision

合計10.184秒（終了処理込み）のうち、初期化を含む応答待ち・受信が9.991秒、98.1%だった。commiter側のJSON解析は合計約0.164秒、選別/Turn検証は約0.020秒。今回の主要な待ち時間はクライアント側の選別ではなく、RPC応答を受け取り終わるまでの区間にある。

特にthread/items/listが513回、RPC全体9.013秒、そのうち待ち・受信8.849秒。次の改善はこの取得経路を対象にする。ただし応答待ちにはサーバーの履歴読込/JSON化/スケジューリング/ローカルpipe転送/クライアントのReadBytesによる受信が混ざっており、サーバー内部の主因を特定したものではない。

## Conditions

前回速度比較の主checkout・.gitignore・同じsince/until・現在cwdのみ・paged100・無制限の条件を固定。保存Git入力を使用し、実履歴取得は1回、並行測定・再試行・モデル呼出しなし。起動バイナリ/source hashとqueryを計測前planに固定。item種別の追加解析は無効。

87thread・対象443Turn・15,097item・42,098,301bytes。606要求で、前回は605要求。live保存履歴のページ構成は変わり得る。同じquery条件と選択結果を確認するが、前回の9.606秒と今回10.181秒の差を計測追加の純粋オーバーヘッドとは扱わない。

## Implementation / validation

captureに--history-timing-logを追加。要求ごとのメソッド/ローカル連番/送信ms/待ち受信ms/外枠JSON解析ms/result解析ms/応答bytes/成功失敗、全体の起動・選別・path・安全性検証・終了を0600の新規JSONへ保存する。本文、path、thread/Turn/item ID、cursor、要求引数、生エラーは記録しない。計測はcontextで明示有効化し、通常時はログを保存しない。

回帰テストで計測有無の操作/依頼/応答の不変、親子時間の非重複、ログに本文を含まないこと、CLI出力と上書き拒否を確認。関連3パッケージのgo test、PoC go vet、test binary/CLI buildが成功。

今回の選択編集は0件で、history complete/unmatched。前回の同条件結果と一致した。選別0.020秒を、対象編集が多数ある場合の上限とは扱わない。path/安全性確認自体は非対象編集と各Turnの依頼に対しても実行している。

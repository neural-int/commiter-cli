# 500件要求・1応答300MB上限の実測

## Goal

承認された500件要求、1応答300MB上限で一度測定する。受信量制限とメモリ監視を実施し、前回の100件方式と同じ現在worktree/期間/Git入力で要求数・速度・取得結果を比較する。

## Result / Decision

正常終了。1応答最大1,426,614bytes（約1.43MB）で300MB上限には達しなかった。取得10.639秒・606要求・42.099MB。前回100件方式は10.181秒・606要求・42.098MBで、今回の500件指定による改善はない。

測定後、既存Turnの同じ先頭ページで100件/500件の指定を各1回確認。100→実返却100、500→実返却100で、どちらもnextCursorあり。500件要求は現在のローカル版のitem取得で100件に抑えられる挙動だった。将来版や別メソッド一般の上限を断定しない。既定paged100を維持し、今回の結果だけで1000件へ進まない。

## Implementation / safeguards

研究用paged500を追加。1JSONL応答を末尾改行込み300,000,000bytesに制限し、固定長のreader断片が上限を超える場合、追記・JSON解析前にresponse_size_limitとして停止する。全取得の累積受信量とは別の制限。無制限履歴モードでもこの1応答制限は解除しない。partial/unavailableとGit fallbackを保持し、完全取得扱いにしない。

これは受信バイト数の上限でありRAM300MBを保証するものではない。Goのappend容量やコピー、サーバー側の応答作成は別にメモリを使う。過大応答の境界は小さな上限を使った回帰テストで検証し、実300MBの負荷テストはしていない。

## Frozen measurement

前回100件計測planの主checkout・.gitignore・since/until・保存Git入力を流用し、modeだけpaged500へ変更。時間/累積受信量は無制限、1応答300MB、安全フィルタ、現在cwdのみの範囲を維持。内訳ログあり、取得は1回、並行取得・再試行・モデル生成なし。source/binary/queryを計測前に私有planへ固定。

前回と今回でメモリ監視の有無等が異なり、単発の0.46秒差を有意な悪化と結論しない。ただし要求数が減らず、500件要求が100件しか返らないことは観測できた。

## Memory observations

約1秒間隔で11回サンプリングした。harnessのRSS最大49,020,928bytes（49.02MB）、App Server子孫のRSS合計最大146,096,128bytes（146.10MB）。それぞれ独立したサンプル最大で、瞬間peakや同時合計peakではない。App Server側はlauncher等の子孫も含む。

macOSのメモリ圧迫値は全サンプルで1（normal）。criticalの4なら測定プロセス群のみ停止する監視を用意したが、発動なし。system-wide Swapoutsは増加なし、Pageoutsは22増加。これらはMac全体の値で他アプリの影響を分離していない。本測定で300MB近辺の応答が安全であることを保証するものではない。

## Validation / correction

関連3パッケージのgo test、PoC go vetと測定バイナリbuildを実施。境界と上限超過のfail-closed、および方式互換性を確認。方式比較fixtureは各subtestでTurn時刻を再生成しており、秒境界をまたいだ実行で出典メタデータの差を検出した。fixtureの時刻を全方式で固定して再検証し成功。実履歴取得の再実行はしていない。
